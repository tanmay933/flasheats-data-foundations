# FlashEats Delivery Reliability

An FDE Data Foundations assignment project that takes fragmented, synthetic client data from multiple operational systems and turns it into a small, dependable pipeline producing trustworthy delivery-reliability KPIs.

> **Data note:** All data in this repository is synthetic. It is generated by `data/generate_data.py` to simulate a fragmented food-delivery environment with inconsistent IDs, schema drift, missing events, and invalid values. It is not real FlashEats data.

---

## Business Question

**How reliable is FlashEats delivery, and where are delays coming from?**

The pipeline combines order, courier, restaurant, and customer-support data to produce a repeatable order-level view of delivery performance.

---

## Stakeholders / Users

- **Operations team** — delivery reliability and KPI tracking
- **Delivery / courier operations** — assignment and transit performance
- **Restaurant operations** — kitchen preparation performance
- **Customer support** — visibility into complaints associated with late deliveries

---

## Decision Supported

The output provides operations teams with a repeatable view of delivery reliability and a first-pass breakdown of where delays are occurring across the delivery workflow.

The delay breakdown is intended to support further operational investigation and prioritization. It is **not causal analysis**.

# Source Systems and Retrieval

The project intentionally simulates fragmented client systems with different data formats and retrieval methods.

| Source | Format | Retrieval Mode | Grain | Key Information | Known Gaps |
|---|---|---|---|---|---|
| Orders DB | SQLite | SQL (`sqlite3`) | 1 row per order | Order ID, restaurant, customer, status, promised time, order total | Duplicate rows, null/non-positive totals |
| Courier Tracking | JSON-backed mock API | API (`requests`) | 1 row per courier event | Assignment, pickup, delivery events and timestamps | Missing events, malformed references, invalid event ordering |
| Restaurant POS | CSV files | Files | 1 restaurant/order preparation record | Accepted and food-ready timestamps | Schema drift, inconsistent IDs, missing preparation timestamps |
| Support Tickets | JSON | Files | 1 row per support ticket | Ticket reason, order reference, ticket timestamp | Null and orphaned order IDs |

This provides three retrieval modes:

- SQL
- API
- File-based retrieval using CSV and JSON

See [diagrams/source_map.md](diagrams/source_map.md) for the detailed source map.

---

## Cross-System Join Key

The canonical business identifier is:

```text
order_id
```

Different systems represent the same order differently:

| System           | Raw Representation       | Normalization                  |
| ---------------- | ------------------------ | ------------------------------ |
| Orders DB        | `1000`                   | Canonical ID                   |
| Courier Tracking | `ORD-1000`               | Remove `ORD-`                  |
| Restaurant POS   | `1000`                   | Canonical ID                   |
| Restaurant POS   | `FE1000`                 | Remove `FE`                    |
| Support Tickets  | `1000` / null / orphaned | Parse and match known order ID |

The transformation layer normalizes these representations before joining the sources.

# Workflow and Data Model

The delivery lifecycle is modeled as:

```text
Placed
  ↓
Accepted
  ↓
Preparing
  ↓
Ready
  ↓
Courier Assigned
  ↓
Picked Up
  ↓
En Route
  ↓
Delivered
```

Orders can also terminate as:

```text
Order
├── Delivered
├── Cancelled
└── Failed
```

A support ticket can optionally be associated with an order.

See [diagrams/workflow_data_model.md](diagrams/workflow_data_model.md) for the complete workflow, order-level model, and metric relationships.

# Pipeline

```text
Raw Sources
    ↓
Ingestion
    ↓
Validation
    ↓
Transformation
    ↓
Metrics
    ↓
outputs/metrics_report.json
```

| Stage          | Module                            | Responsibility                                                                                            |
| -------------- | --------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Ingestion      | `src/ingestion/ingest.py`         | Retrieves SQL, API, CSV, and JSON sources without cleaning them                                           |
| Validation     | `src/validation/validate.py`      | Detects and reports data-quality issues                                                                   |
| Transformation | `src/transformation/transform.py` | Normalizes IDs, handles duplicates, normalizes timestamps, joins sources, and creates order-level records |
| Metrics        | `src/metrics/metrics.py`          | Calculates the five business KPIs                                                                         |
| Orchestration  | `run_pipeline.py`                 | Runs the complete pipeline and writes final outputs                                                       |

### Data-quality principle

Raw inputs under `data/raw/` are not modified by the pipeline.

Validation identifies quality issues before transformation. The pipeline does not silently correct problematic records. Where required data is unavailable or cannot be safely joined, the affected metric is left unavailable and the exclusion is recorded.

# KPIs / Metrics

## 1. On-Time Delivery Rate

**36.31%**

```text
114 / 314
```

The denominator contains completed orders with a usable `on_time` or `late` classification.

26 completed orders were excluded because the required delivery information was unavailable or invalid.

---

## 2. Average End-to-End Delivery Time

**46.5 minutes**

Measured from order placement to delivery for completed orders with usable timestamps.

Component averages:

| Component      |   Average |
| -------------- | --------: |
| Kitchen time   | 17.12 min |
| Courier time   | 19.77 min |
| Assignment lag | 25.54 min |

Each component average uses the orders for which that specific set of timestamps is available.

---

## 3. Delay Attribution

Among **200 late orders with usable attribution**:

| Classification   | Count | Percentage |
| ---------------- | ----: | ---------: |
| Assignment delay |   133 |      66.5% |
| Mixed / unclear  |    66 |      33.0% |
| Courier delay    |     1 |       0.5% |
| Kitchen delay    |     0 |       0.0% |

The classification uses explicit operational thresholds:

```text
Kitchen time   > 20 minutes
Courier time   > 22 minutes
Assignment lag > 8 minutes
```

A single threshold breach is attributed to that leg.

Zero or multiple threshold breaches are classified as:

```text
mixed/unclear
```

> **Important:** This is a threshold-based operational classification, not causal analysis. It does not establish that a particular workflow stage caused a delay.

---

## 4. Failure / Cancellation Rate

**15.0%**

```text
60 / 400 unique orders
```

This combines:

```text
32 cancelled
28 failed
```

## 5. Late-Delivery Complaint Rate

**9.41%**

```text
32 / 340 completed orders
```

Only tickets successfully linked to a known order ID are included.

A support ticket does not prove that an order was actually late, and a late order does not necessarily produce a support ticket. This metric reports the observed relationship in the available data.

# Known / Unknown / Assumption / Limitation

## Known

- The five KPIs are directly calculated from the transformed order-level dataset.
- The pipeline records the number of retrieved, transformed, excluded, and unlinked records.
- Validation findings are structured by source, rule, severity, and affected count.
- The current pipeline produces a reproducible JSON metrics report.

## Unknown

- 26 completed orders do not have sufficient information for a usable on-time/late classification.
- The delay attribution logic cannot establish causal relationships.
- Tickets with null or orphaned order IDs cannot be associated with a specific known order.
- Individual component metrics may use different subsets of orders because timestamp availability differs by source.

## Assumptions

- Orders DB and courier timestamps are treated as UTC.
- Restaurant POS timestamps contain no timezone information.
- The date in the restaurant CSV filename is used as the timestamp date.
- Restaurant POS timestamps are assumed to be IST and converted to UTC.
- Malformed courier references are never force-matched using heuristics.
- Restaurant IDs using the `FE` prefix are normalized by removing that prefix.
- Support tickets are linked only when their order ID parses to a known order.

## Limitations

- Delay attribution uses simple thresholds rather than statistical or causal analysis.
- Missing or invalid timestamps result in unavailable/null metrics instead of guessed values.
- The failure/cancellation metric does not distinguish cancellation or failure stage.
- The support-ticket metric only includes tickets that can be linked to known orders.
- Synthetic data does not represent actual FlashEats production behavior.

# Summary

This project demonstrates an end-to-end FDE workflow:

```text
Understand fragmented sources
        ↓
Retrieve data using multiple modes
        ↓
Profile and validate data quality
        ↓
Normalize and join operational data
        ↓
Build an order-level model
        ↓
Calculate business KPIs
        ↓
Produce a reproducible metrics report
```

The focus is not on project size or UI polish. The objective is a **trustworthy path from fragmented client systems to a business decision**, with assumptions, data-quality issues, exclusions, and limitations made explicit.
